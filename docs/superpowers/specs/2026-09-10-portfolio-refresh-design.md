# Portfolio Refresh — Design

**Date:** 2026-09-10
**Site:** chrishat310.github.io (al-folio / Jekyll, GitHub Pages)
**Status:** Design approved, pending spec review

---

## 1. Problem

The site is content-rich and structurally flat. Fifteen project pages of 370–540 words each, all at equal visual weight, in stock al-folio purple. A reviewer cannot tell which two projects the owner wants to be judged on, and nothing on the site has changed since July 2026.

Measured against the portfolio criteria the owner supplied, four gaps:

| Criterion | Current state |
|---|---|
| 3–4 main projects | 15, all equal weight |
| Visuals as the primary communication tool | Prose-primary; 6 projects have only a thumbnail |
| Objective → contribution → results vs objective | Narrative essays; nothing extractable in a 30-second skim |
| One project per page | Already satisfied |

Three projects and two publications present in `cv.md` are absent from the site entirely.

## 2. Audience and positioning

**Primary audience: industry ML and simulation hiring.** (The academic/PhD track was paused 2026-09-09; the site should not be tuned for admissions committees.)

**Narrative: the engineering→ML wedge.** Arrived at machine learning through mechanical engineering and multi-physics simulation, and builds ML on top of that foundation. Every structural choice below serves this claim.

Positioning line (compressed from the existing about page, no new claims):
> Machine learning for engineering design. From carbon-fibre foils to Bayesian optimisation.

## 3. Deliverables

Two outputs, one source. No duplicated content, no drift.

```
_projects/*.md                      single source of truth
   │
   ├──► Jekyll ──► chrishat310.github.io      web: 18 projects, index, live demo
   │
   └──► Jekyll ──► /portfolio/print/ ──► Playwright ──► portfolio.pdf
                   flat print variant           4 flagships, one per page + cover
```

The website is built first; the PDF is generated from it. The PDF is regenerated by one command after any content edit.

**Consequence:** the interactive demo cannot exist in the PDF. That page carries a static GP-posterior figure captioned with a URL to the live version. The PDF must therefore stand on figures alone.

## 5. Content model

The central structural fix: **the criteria's five points become named frontmatter fields, not prose.** This makes a 30-second skim possible and drives both the web page and the PDF page from the same data.

```yaml
---
layout: flagship          # or: index
title: NOVA Electric Racing — Bike Chassis
tier: flagship
category: mechanical
objective: >              # criterion 1 — what the design had to achieve
role: >                   # criterion 3 — specific personal contribution
methods: [Ansys, FEM, composites]   # criterion 4 — orientation, not exhaustive
result: >                 # criterion 5 — outcome evaluated against objective
metrics:                  # optional; renders as a stat row
  - {label: Validated to, value: 2.5× working load}
  - {label: Components analysed, value: 20+}
  - {label: Team led, value: 6}
figures:                  # criterion 2 — plural, required for flagships
  - {path: ..., caption: ...}
importance: 1
---

Narrative prose continues below, unchanged in voice.
```

**Structured head, narrative tail.** The head satisfies the criteria and the skim; the tail preserves the existing first-person writing, which is a genuine asset and is not being rewritten.

Flagships require a minimum of **three figures** and at least one entry in `metrics`. Index entries require one figure and a one-line result.

## 6. Visual design — register C

Selected by the owner from three options after the trade-offs were presented.

**Baseline:** the approved mockup — gradient hero, white body, rounded cards, pill buttons.

**Three de-risking constraints applied within that direction:**

1. **Gradient confined to the hero band.** Everything below sits on white or a near-white neutral, so FEM plots, field solutions and GP posteriors never compete with a saturated ground.
2. **Accent hue sampled from the owner's own figures** rather than default violet→indigo, which is the house style of most template portfolios. Final hue proposed at implementation and approved before rollout; the mockup palette is the fallback.
3. **Flat print variant** — no gradients in the PDF, which band badly in export.

**Type:** an engineering-flavoured pairing rather than the default Inter/Space Grotesk. Display and body from one family with real weight range; monospace for data labels, metrics and captions.

**Motion:** scroll-triggered reveals on section entry and hover depth on cards. CSS plus `IntersectionObserver`; no React, no framework. Every animated element has a visible resting state and the page is fully readable with JavaScript disabled. `prefers-reduced-motion` disables all of it.

**Dark mode:** al-folio already ships it and it stays. The gradient needs a dark-ground variant.

## 7. The Bayesian optimisation demo

The site's one interactive set-piece. Subject chosen because it collapses the thesis, both publications, the BayesOpt-drug project and the GP air-quality project into a single artifact — and because it makes the owner's stated interest in uncertainty visible rather than asserted.

**Teaser** — replaces the static hero on the landing page.
- 1D objective, GP with RBF kernel, expected improvement
- Auto-runs ~8 iterations on load, then loops
- Renders posterior mean, uncertainty band, observed samples, and the next-sample location
- No controls. Links through to the full version.

**Full version** — embedded in the Mixed-Variable BO project page, where the context justifies the controls.
- Acquisition function switch (EI / UCB / PI)
- Kernel lengthscale
- Step and restart
- Links to the BOCoDe arXiv preprint

**Implementation:** vanilla JS on Canvas. No plotting library — the maths is a few dozen lines and a dependency is not worth the weight. Static fallback figure when JavaScript is unavailable.

## 8. Constraints

**Truth-first.** No fact, metric, tool, outcome or ownership claim enters the site unless it is already in `cv.md`, an existing repo file, or stated by the owner directly. Where a stronger phrasing needs a fact that does not exist, the weaker phrasing ships.

**Embargoed-venue suppression (load-bearing).** `cv.md` carries a note naming this site specifically: BOCoDe's target venue forbids non-anonymous online material from stating or implying where the paper was submitted, on pain of summary rejection. BOCoDe goes up as an arXiv preprint with **no venue named** until the decision is out. This applies to the site, the PDF, and any generated CV.

**Misattributed-repository removal.** `_data/repositories.yml` currently lists a repository publicly among the owner's repos that is not his work. The owner has confirmed this. It is removed. This is an attribution risk, not a tidying preference.

**Private repos.** Project code is not public, so per-project code links are not available. Proof has to rest on figures and precisely stated results — which is what the criteria ask for regardless.

**Hitachi is unpublishable — resolved.** The HV-capacitor work is not published and cannot carry public figures, so it cannot satisfy the flagship figure minimum. It is **demoted to a full index page** under Simulation, and the EV battery-enclosure project takes flagship slot 3. The industry experience remains visible via the CV, the about page and its index entry; what it loses is a flagship slot it could not have filled.

No figure, plot, geometry or result originating from the Hitachi internship enters the site or the PDF until the owner confirms it is clearable.

## 11. Success criteria

1. A reviewer can identify the four flagship projects within five seconds of landing.
2. Each flagship page yields objective, contribution and result within a 30-second skim, without reading prose.
3. Every flagship carries at least three figures and at least one quantified result.
4. `portfolio.pdf` regenerates from site content in one command, and its flagship pages carry the same objective, contribution, metrics, figures and result as the web pages — the interactive demo excepted, per §3.
5. The live demo runs on load and degrades to a static figure without JavaScript.
6. No venue is named for BOCoDe anywhere in the built output.
7. The misattributed third-party repository does not appear anywhere in the built output.
8. No claim on the site is unsupported by `cv.md`, repo files, or the owner's direct statements.
